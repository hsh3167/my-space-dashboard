# 증권사 파일 가져오기 및 배포

## 업로드 규칙

1. Supabase 설정 및 본인 로그인 검증을 끝낸 후에만 업로드합니다. 테스트는 합성 데이터만 사용합니다. 실제 증권사 파일의 모든 내보내기 형식을 확인한 것은 아닙니다.
2. 계좌 추가에서 **계좌번호 대신 별칭**을 정하고 일반 증권/퇴직연금을 구분합니다. 다른 계좌의 파일을 같은 별칭으로 합치지 마세요.
3. CSV(UTF-8/BOM/EUC-KR, 쉼표·탭·세미콜론) 또는 값만 있는 XLSX를 선택합니다. XLS, XLSM, 암호화 파일, 수식/외부 연결이 있는 XLSX는 지원하지 않습니다. 5MB/5,000종목/128열, 시트 최대 20개, XLSX 압축 해제 총 20MB 제한이 있습니다. XLSX는 제한 시간 15초의 Web Worker에서 처리합니다.
4. XLSX 시트와 헤더 행을 선택합니다. `종목명/상품명`, `보유수량/잔고수량`, `평가금액/평가액`, `매입금액/취득금액` 등을 자동 매핑하며 다른 열 이름은 직접 매핑할 수 있습니다. 종목코드/통화는 선택 항목입니다. 단가가 아닌 **총액**을 선택합니다.
5. 금액 단위를 원/천원/백만원 중 선택합니다. 모든 금액은 KRW 환산 금액이어야 합니다. 외화 원금은 자동 환전하지 않습니다. 통화 열이 KRW가 아니면 저장을 차단합니다. 통화 열이 없는 파일은 사용자가 원화 총액임을 확인해야 합니다.
6. 평가 기준일과 예수금을 입력하고, 미리보기 및 모든 검증 오류를 확인합니다. `합계/소계/총계/total` 행은 제외하며 중복 종목 행·음수·잘못된 수치·민감정보가 포함된 식별 필드는 차단합니다. 계좌번호·고객명 등 고객정보 열은 직접 매핑해도 저장할 수 없습니다.
7. **보유종목 전체 교체**를 확인하고 저장합니다. 선택한 계좌의 보유종목 전체가 교체됩니다. 새 잔액은 평가금액 합계+예수금이며, 기존 관련 부채는 유지됩니다. 부분 포트폴리오 파일을 올리지 마세요. 빈 파일은 보유종목을 삭제하는 용도로 사용할 수 없습니다.
8. 서버는 정규화·정렬한 필드와 예수금으로 SHA-256 지문을 계산합니다. 동일 계좌·동일 기준일·동일 내용은 중복 방지 제약으로 차단됩니다. 파일명이나 행 순서를 바꿔도 중복됩니다. 새 기준일은 새 평가로 인정합니다. 현재 기준일보다 오래된 파일로 잔액을 되돌릴 수 없습니다.
9. 업로드 이력, 종목 교체, 잔액 및 **오늘의 합산 자산 스냅샷**이 한 트랜잭션으로 저장됩니다. 과거 일자의 파일을 올려도 과거 전체 자산 이력을 추정하여 채우지 않습니다. 월별 그래프는 실제로 저장된 각 월의 마지막 스냅샷을 표시합니다.

원본 파일·파일명·계좌번호는 브라우저에서 서버로 전송하지 않습니다. 매핑에 필요한 원본 셀은 임시 메모리에만 있다가 미리보기 지우기/성공/탭 이동/로그아웃 시 해제됩니다. 서버에는 허용된 종목 필드·별칭 계좌의 ID·평가 기준일·예수금만 전송합니다. DB 이력에는 행 수와 정규화 지문만 추가합니다. 앱은 금융 데이터의 다운로드/내보내기를 추가하지 않으며 기존 JSON 백업에는 링크 데이터만 포함됩니다.

## 개발 및 정적 배포

```sh
npm ci
npm test
npm run build       # 고정된 의존성으로 XLSX Worker를 재생성
npm run build:site  # 명시된 정적 파일만 _site/에 복사
npm run serve      # 저장소 루트에서 개발 서버
```

Node 22 이상은 개발/테스트/Worker 재생성에 사용합니다. 생성된 Worker는 저장소에 포함되어 있으므로 정적 호스팅에서는 Node/서버/런타임 패키지 설치가 필요 없습니다. 자산관리 딥링크는 `?view=assets`이며 하위 GitHub Pages 경로에서도 상대 경로를 사용합니다.

공개 Pages 아티팩트에는 HTML/CSS/JS와 가상 샘플만 허용 목록으로 복사합니다. SQL·테스트·node_modules·로컬 설정·파일 원본은 아티팩트에 넣지 않습니다. `.gitignore`는 `.env*`, `private/`, `uploads/`, CSV/XLSX 등의 실수 커밋을 방지하지만 유일한 보안 경계는 아닙니다. 파일을 강제로 추가하거나 개인정보를 코드에 붙여 넣지 마세요.

### GitHub Pages 게시 절차

- 기존 **Deploy from a branch → main / root** 방식을 유지할 수도 있습니다. 모든 런타임 파일과 생성된 Worker가 커밋되어 있으므로 main 반영 후 기존 방식으로 게시됩니다. 이 방식은 별도 파일 빌드 없이 동작하며, URL/공개 키는 자산 화면의 연결 설정에서 입력할 수 있습니다.
- 정적 파일 허용 목록과 GitHub variables 주입을 사용하려면 Settings → Pages → Source를 **GitHub Actions**로 설정합니다. Actions의 **Deploy My Space to Pages**를 main 브랜치에서 수동 실행합니다. 공개 기본 설정을 넣고 싶으면 repository variables에 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`를 등록합니다. 둘 다 없으면 샘플 모드로 배포됩니다. service_role/secret 키는 거부됩니다.
- **Checks** 워크플로는 단위/DOM/DB 정책 테스트, Worker 재생성 일치, 프로덕션 의존성 취약점 검사와 Playwright/Chromium의 실제 브라우저 검증을 수행합니다. 사용자가 브라우저 도구 제한을 해제하여 Chromium 검증을 사용합니다.
- 게시 후 데스크톱과 모바일로 기존 3개 탭/검색/편집/백업·복원을 확인하고, 자산 탭의 샘플·로그인·로그아웃·합성 CSV/XLSX 업로드·중복 거부를 확인합니다. 인증 전 금융 API 요청이 없어야 하며 로그아웃 후 금액이 지워져야 합니다.

실제 Supabase 프로젝트 검증에는 사용자 프로젝트 설정이 필요합니다. 초기에는 GitHub API/Pages 접근이 차단되었으나 이후 API와 TLS 검증 HTTP 접근은 동작하며 main/root의 GitHub Pages 게시를 확인했습니다. 이 클라우드의 Chromium은 환경 프록시 CA를 신뢰하지 않으므로 공개 페이지의 브라우저 검증은 **Verify deployed My Space** 수동 워크플로를 사용합니다. 인증서 검증을 비활성화하지 않습니다. 로컬 정적 서버에서 360/390/768/1440px의 실제 Chromium 검증은 통과했으며, 로그인과 업로드 검증은 합성 Supabase HTTP 응답을 사용했습니다. 호스팅 DB 검증은 별도로 완료해야 합니다.

### 브라우저 테스트 재현

```sh
python3 -m pip install -r requirements-browser.txt
python3 -m playwright install chromium
# 별도 터미널에서 정적 서버를 실행한 뒤:
python3 scripts/browser-smoke.py
```

시스템 `/usr/bin/chromium`이 있으면 우선 사용하고, 없으면 Playwright Chromium을 사용합니다. `CHROMIUM_EXECUTABLE`로 경로를 지정할 수도 있습니다. 이 스크립트는 격리된 브라우저와 합성 계좌/파일만 사용합니다. 실제 Supabase 호스트에는 연결하지 않습니다. 선택 인자로 검증 대상 사이트 주소를 지정할 수 있습니다.
