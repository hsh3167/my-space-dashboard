# 자산관리 개발 계획과 검증 기록

기존 개인용·업무용·AI 사무실과 링크 저장/백업은 유지한다. 자금 확보 시뮬레이터는 범위에서 제외한다. 공개 저장소에는 합성 샘플과 테스트만 넣는다.

1. `feat: add sample asset management workspace`: 기존 다크 테마에 자산관리 작업 공간, 총자산/순자산, 계좌 구성, 보유종목, 월별 그래프, 주택 납부 일정을 추가한다. 집계·차트·기존 링크 기능 회귀 테스트 후 커밋한다.
2. `feat: secure asset workspace with Supabase auth and RLS`: 자산 화면에만 이메일/비밀번호 로그인을 적용한다. 세션은 메모리에만 두며 로그인/허용 사용자 확인 전에 금융 테이블을 조회하지 않는다. 본인 UUID 한 명만 DB에서 허용하고 모든 테이블에 RLS를 적용한다. 실제 PostgreSQL 엔진 기반 정책 테스트, 가짜 응답 기반 인증 경계 테스트 후 커밋한다.
3. `feat: import Samsung Securities CSV and XLSX safely`: 로컬 파일 파싱, 일반/퇴직연금 구분, 자동/수동 매핑, 미리보기/검증, 서버 측 원자적 중복 방지를 구현한다. 원본 파일·파일명·계좌번호·주민번호는 저장하지 않는다. 합성 파일로 파싱/업로드 테스트 후 커밋한다.

처음에는 사용자 지정 EGO-LITE 연결을 기다렸다. 이후 사용자가 브라우저 도구 제한을 해제하여 Playwright/Chromium으로 실제 브라우저 검증을 수행한다. 아래 단계별 기록의 'EGO-LITE 대기'는 당시 상태이며 최신 검증 결과를 함께 확인한다.

외부 선행 작업: Supabase 프로젝트 및 본인 Auth 계정 생성, SQL 마이그레이션 실행, 사용자 UUID 허용 등록, 공개 URL/publishable 키 설정. 비밀 키는 프런트엔드·Git에 넣지 않는다. GitHub Pages 게시 후 기존 탭과 자산 탭을 다시 검증한다. 실제 금융정보는 모든 테스트를 통과하고 사용자가 연결을 완료하기 전까지 사용하지 않는다.

실행 결과와 남은 외부 작업은 각 단계에서 이 문서 및 설정 가이드에 기록한다.

## 1단계 검증

`npm test`: 7개 통과 (집계/차트/출력 이스케이프 및 기존 탭·검색·링크 생성/수정/삭제·백업·딥링크 DOM 회귀). `node --check app.js`, `git diff --check` 통과. 실제 브라우저/모바일 렌더링은 EGO-LITE 연결 전이므로 미검증.

## 2단계 검증

인증 전/다른 사용자/익명 금융 조회 차단, 로그아웃 중 지연 응답 무효화, 비밀 키 거부 및 DOM 로그인 경계 테스트 추가. PGlite의 PostgreSQL 엔진에서 실제 마이그레이션/RLS 정책을 실행했다. `npm test`: 19개 통과. 실제 Supabase 프로젝트/계정이 없어 호스팅 DB·실제 Auth 검증은 미실행. EGO-LITE 검증도 연결 대기. 사용자 외부 설정 절차는 `docs/supabase-setup.md` 참조.

## 3단계 검증과 인계

`npm ci --cache /workspace/.cache/myspace-npm`, `npm run build:site`, `npm test`: 35개 통과, 실패/스킵 0. 합성 CSV/EUC-KR/XLSX, 수동 매핑/원화 단위/고객정보 열 차단, 미리보기/확인 경계, 실제 Worker 번들 프로토콜, 서버 중복 차단/새 기준일 교체/이전 기준일 거부/잔액 제약 실패 시 전체 롤백을 확인했다. `npm audit --omit=dev --audit-level=high`: 취약점 0. Worker 재빌드는 바이트 단위 일치. 개발 서버와 정적 배포 아티팩트의 HTML/JS/CSS 경로를 HTTP로 확인했다. 기존 온보딩 서버는 중단·재개 사이 응답이 끊겨 본 작업에서 시작했던 프로세스만 재시작했고 HTTP 검증을 통과했다.

실제 금융정보와 실제 증권사 파일은 사용하지 않았다. 단계별 커밋은 `feat/asset-management` 브랜치에 올리며 main/운영 사이트 반영은 아직 하지 않았다. EGO-LITE 연결이 없으므로 실제 브라우저·모바일 화면 검증은 미실행. Supabase 프로젝트가 없어 실제 Auth/호스팅 DB 통합 검증은 미실행. GitHub API/Pages 읽기는 프록시 403으로 차단되어 실제 게시 상태를 확인하지 못했다. 1~3단계 코드 구현과 로컬 자동 검증을 마쳤으나 운영 준비/배포 완료를 주장하지 않는다.

환경 설정 초안에는 npm 설치/시작 지침을 갱신하고 기존 외부 자산 도메인을 유지하며 api.github.com, hsh3167.github.io를 추가했다. 초안 저장은 런타임 적용·환경 게시·앱 배포가 아니다. 사용자가 환경 설정을 저장/게시한 뒤 해당 네트워크와 복원 상태를 다시 확인해야 한다. Supabase 생성/본인 UUID 등록/공개 연결 설정 및 게시 절차는 docs/supabase-setup.md, docs/import-and-deploy.md에 정리했다.

## 실제 브라우저 검증 및 로그인 수정

사용자가 브라우저 도구 제한을 해제한 뒤 Playwright 1.62.0과 시스템 Chromium으로 검증했다. 실제 브라우저에서 fetch를 AssetClient의 메서드로 호출하면 `Illegal invocation`이 발생하는 문제가 발견되어 글로벌 객체에 바인딩하도록 수정하고 회귀 테스트를 추가했다.

수정 후 개발 서버와 허용 목록 기반 정적 배포 아티팩트에서 각각 11개 브라우저 시나리오 그룹을 통과했다. 기존 탭/검색/링크 생성·수정·삭제/새로고침 저장/JSON 백업·복원/초기화, 360/390/768/1440px 전체 탭 가로 넘침 검사, 자산 샘플 금액, 인증 전 조회 없음/비허용 사용자 차단/공개키 설정, 본인 승인 후 표시, 계좌/일정 생성과 납부 처리, 실제 Web Worker의 XLSX 읽기와 퇴직연금 구분, CSV 미리보기·저장·중복 거부, 오류 파일 차단, 로그아웃 중 지연 응답 무효화 및 딥링크를 확인했다. 미처리 JavaScript 오류 0건. 데스크톱/390px 스크린샷도 확인했다.

단위/DOM/DB 테스트 36개 통과, 배포 빌드 통과, 프로덕션 취약점 0건. 브라우저 검증은 격리된 컨텍스트와 합성 Supabase HTTP 응답만 사용했다. 실제 프로젝트의 인증/네트워크/RLS는 프로젝트 생성 후 별도로 검증해야 한다. 재현 스크립트는 scripts/browser-smoke.py이며 Checks CI에도 포함했다.
